amis AI Chat 低代码组件技术方案

1. 背景与定位

目标:在 amis 中新增 ai-chat 渲染器,让低代码用户通过 JSON 配置即可得到一个完整的 AI 对话组件(消息流 / 流式输出 / 工具调用可视化 / 思考过程 / 数据域联动),对接任何 AG-UI 协议后端。同一个实现同时以普通 React 组件形式对外发布(见 D6),脱离 amis 渲染上下文也可 <Chat endpoint="..." /> 直接使用。

与 docs/design.html(amis-editor AI Agent 方案)的关系:同一后端,两个消费端。design.html 是"编辑器内 Copilot"(Agent 修改 schema,面向开发者);本方案是"页面级 chat 组件"(面向最终用户页面的通用对话能力)。二者复用同一个 AG-UI 协议层与同一个后端 amis-agent-starter(POST /amis-agent/chat,SSE 事件流)。

2. 业界参考与取舍

参考值得吸收不能照搬的原因
Semi Design Chat 概念模型:Message(role/content/status)、roleConfig、mode(bubble/noBubble)、hints 提示、SSE 受控更新、stopGenerator、消息操作回调(复制/反馈/重发) amis-ui 是零第三方 UI 依赖的纯组件库 + CSS 变量三层主题体系(SUIT 命名);引入外部组件库会带入整棵依赖树与第二套主题/样式体系,破坏多主题(cxd/antd/ang/dark)能力
TDesign react-chat ChatStreamer 思路:SSE 增量 append + 分片渲染防长文卡顿;思考过程(reasoning)折叠展示
CopilotKit Agent 框架分层概念(CopilotKitProvider / runtime / useCopilotChat);AG-UI 协议正是其主推的传输标准 它是 Next.js 代码优先的应用框架,方向与"JSON 配置生成页面"相反;onboarding 页面实际是让编码 agent 在当前目录执行 npx copilotkit onboard 脚手架命令,不能在 amis 仓库执行
assistant-ui Runtime 抽象层(协议与 UI 分离)分层方式 同上;且默认样式依赖 Tailwind

3. 关键设计决策

D1 · UI 完全自研,不引入任何 chat 组件库。仅吸收上表概念模型。amis-ui 已有 Markdown 组件可直接复用为消息内容渲染器;自研件纳入 CSS 变量主题体系,四主题自动适配。
D2 · 协议绑定 AG-UI 标准(16 类标准事件)。后端 amis-agent-starter 已按 AG-UI(SSE)实现。前端按标准事件模型实现(RUN_* / TEXT_MESSAGE_* / TOOL_CALL_* / STATE_SNAPSHOT / STATE_DELTA / MESSAGES_SNAPSHOT / CUSTOM / RAW),不私有扩展;未知事件类型静默忽略并 console.warn,保证前向兼容。
D3 · 请求能力走 env 扩展点 env.aguiFetcher,并内置默认实现。原因:amis 自身不发请求,全走 env;env.fetcher 的契约是"一次性完整响应(Promise<Payload>)",SSE 是持续回调,硬塞会破坏所有宿主的 fetcher 实现。新增可选 env 扩展点(签名:aguiFetcher(endpoint, input, callbacks) => {abort},callbacks 含 onEvent/onError/onDone),默认实现用原生 fetch + ReadableStream——宿主零改造即可用,需要统一鉴权/网关时覆盖即可。与 enableAMISDebug 一致的全局开关可打印事件流日志。
D4 · AG-UI 协议层放 amis-core(新目录 src/ai/),不放 amis。协议解码与事件归并是纯逻辑、零 UI 依赖;且 design.html 的"编辑器 Copilot 面板"是第二个消费端,放 core 一处实现两端复用。不建 MST store:消息状态用组件内 useReducer(src/ai/reducer.ts 纯函数)——流式高频更新下 MST 事务是负担,消息列表也无需进数据域;renderer 无 storeType 一样工作,STATE_DELTA 才是数据域联动通道(见 D5)。
D5 · chat 是数据链的一环,不是孤岛。发送时从当前数据域组装 RunAgentInput.context/state;收到 STATE_SNAPSHOT/STATE_DELTA(JSON Patch)时写回数据域,页面其他组件(表格/表单)实时联动;消息完成/出错派发 amis 事件(onEvent),可接任意动作。这是"低代码 chat"与"普通聊天组件"的本质差异。
D6 · 实现一份,出口两个(普通 React 组件 + amis 渲染器)。核心实现在 amis-ui 的 <Chat> 组合件:themeable 纯 React 组件,内部完成协议接线(直接用 src/ai 的 runAgent 默认实现,或由 props 注入 fetcher),禁止出现任何 amis 渲染上下文依赖(render/env/数据域)。
  出口 A · 普通 React:import \{ Chat \} from 'amis-ui' + 主题 css,开箱即用,请求不走 env(这正是 D3 把默认实现放协议层的原因);
  出口 B · amis 渲染器:AIChat.tsx 是薄壳——schema→props 映射、注入 env.aguiFetcher、组装数据域 context、STATE 回写数据域、dispatchEvent。壳不写 UI。

5. 配置模型(Schema)

{
  "type": "ai-chat",
  "endpoint": "/amis-agent/chat",        // AG-UI 端点,支持 ${xxx} 模板
  "title": "智能助手",
  "welcome": "你好,我是页面助手",          // 可为富文本 markdown
  "hints": ["帮我总结数据", "生成周报"],   // 空态提示语,点击即发送
  "roles": {                              // 对应 Semi roleConfig 概念
    "user":      { "name": "我",       "avatar": "...", "color": "blue" },
    "assistant": { "name": "助手",     "avatar": "..." }
  },
  "mode": "bubble",                       // bubble | noBubble | userBubble
  "agentContext": {                       // 发送时从数据域组装(D5)
    "pageData": "${PAGE_DATA}",           // 任意数据映射,进 RunAgentInput.context
    "userId": "${user.id}"
  },
  "stateKey": "chatState",                // STATE_SNAPSHOT/DELTA 写回数据域的 key
  "features": {
    "showThinking": true,                 // 思考过程折叠块
    "showToolCalls": true,                // 工具调用卡片(名称/参数/结果/状态)
    "showStop": true,                     // 停止生成
    "feedback": true,                     // 点赞点踩(onEvent 可上报)
    "sendHotKey": "enter"                 // enter | shift+enter
  },
  "onEvent": {                            // 标准 amis 事件动作
    "finish":    { "actions": [{ "actionType": "toast", ... }] },
    "error":     { "actions": [...] },
    "sendMessage": { "actions": [...] }
  }
}

UI 消息模型内部对齐 Semi 的 Message 概念并扩展 agent 语义:{ id, role, content, status: loading|streaming|complete|error, thinking?, toolCalls?: [{name,args,state,result}] }。消息状态由 Chat 组合件内部 useReducer 管理(reducer 为 src/ai/reducer.ts 纯函数),不建 MST store、无 storeType——流式高频更新不触发整页重渲,STATE 联动走回调而非 store(见 D4/D6)。

协议决策:不走自定义扩展字段,采用 AG-UI 类型化 content 数组——纯文本消息 content 保持 string(兼容所有实现),带附件时为 [{type:'text',text},{type:'image',source:{type:'data',value:'<裸base64>',mimeType}}](source 另支持 url 形态)。依据:反编译 agentscope-extensions-agui 2.0.4(用户后端实际版本)确认 AguiMessage.content 反序列化原生接受 string | InputContent[],@JsonTypeInfo(property='type') 判别 text/image/audio/video 块与 data/url 源,并自动转模型侧多模态请求——后端零改动。document 块 agentscope 会以 RUN_ERROR 拒绝,前端不分派。
UI 形态:输入胶囊左下回形针按钮(Lucide paperclip,图标体系 chat-*)→ 隐藏 file input(multiple)→ FileReader 读 dataURL → chips 缩略图暂存(可删)→ 发送;文本或附件任一非空即可发,纯图片消息不产生空 text 块;用户气泡渲染附件缩略图(点击新标签页看原图)。校验:单文件 5MB/最多 9 张(可配),超限行内红字 3s 自动消失(组件无 toast 依赖)。
落点:协议类型与组装在 amis-core types.ts(AguiContentBlock/ChatAttachment)+reducer.ts(toAguiMessage/attachmentToBlock 纯函数,SEND 带 attachments);UI 在 amis-ui ChatInput/Chat/ChatMessage + _chat.scss(暗色/CSS 变量适配);渲染器 4 个 schema 字段(enableAttachment 默认 false/attachmentAccept=image/*/attachmentMaxSize=5MB/attachmentMaxCount=9),sendMessage 事件携带附件元信息;编辑器插件功能开关分组 4 控件(visibleOn 联动)。
验证:测试 25/25(reducer 5 + 渲染器 3 端到端:jsdom FileReader 真读 dataURL 断言协议形状);typecheck/stylelint 通过;真实链路端到端——发送 80×60 纯红 PNG,GLM 视觉模型回复"偏珊瑚色的红色,色值约 #E8534F"(实际 #E84C4C,识别准确)。demo 页双栏均开启附件。
